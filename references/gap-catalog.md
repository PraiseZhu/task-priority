# 对抗质询标准弹药库（gap-catalog）

> 来源：2026-08 从 75 份 `~/.claude/.goal/` 台账 + 15 份三审 verdict + PR 历史实测挖出。全部为真实数据。
> 用途：Phase 4 对抗质询 sub 的输入材料——只挑「漏了什么 + 哪些 n_a 敷衍」，不报泛泛「可以更好」。

|---|---|---|---|
| 1 | **fail-open/fail-closed 契约不清晰** | #466 / #442 / #571-577 | 最高频 |
| 2 | **共享状态多写者并发一致性** | #442 / #444 / #467 deposit 棘轮、#466 台账清空、#564 跨 run 污染 | |

| 4 | **文档/声明与实际不同步** | #466 契约降标、#457「零改写」实携修复、#481 断言换锚不锁值 | |

## ② 7 例「计划阶段就该想到」的遗漏

1. **#442**：main.js 头注释早写明 fsList 两类不可信形状，读路径实现完全没落实防护——契约已知但未做覆盖分析
2. **#481**：pre-push 剥离 git env 最初只 unset 3 项，未查 git 官方权威清单（实际 15 项）——边界条件未穷举
3. **#466**：docs/loops/bug-doctor.md 早期承诺的能力（React baseline / verify:logging 接入）从未实现，直到该 PR 才如实降标——前期承诺超出可交付范围
4. **#564**：issue #560 对「并发互清」的根因判断本身有误（真因是无 runId 去重，不是进程互清）——前期诊断根因分析有误
5. **#456/#457**：AST 门禁最初设计没考虑转发调用、动态 import、改扩展名三种绕过——安全门禁覆盖面设计遗漏
6. **#483**：Playwright waitForFunction 不 await async 谓词，全仓 19 处从一开始未意识到该库语义陷阱——第三方库 API 语义前期调研缺失
7. **#444**：作者自陈 rebase 整合后的最终树「没有任何审查席看过」——计划阶段未预留「结构变更后需重新过审」检查点

> 质询角度（7 类遗漏各自对应一个问法）：
> 1 契约已知的不可信形状 → 读路径做了防护吗？
> 2 边界条件 → 权威清单查全了吗？
> 3 承诺 vs 交付 → 计划里承诺的能力真的在交付物里吗？
> 4 根因 → 诊断有反证实验吗（不是「看起来对」）？
> 5 门禁 → 绕过路径枚举过吗（转发/动态/别名/扩展名）？
> 6 三方库 → API 语义陷阱查过文档/源码吗？
> 7 结构变更 → 计划预留了「结构变更后重新过审」检查点吗？

## ③ 6 个复发 invariant 家族（15 份三审 verdict 里 12 条 major 实为这 6 族）

| 家族 | 次数 | 原文（verdict 措辞） |
|---|---|---|
| **F1-untrusted-resource-module-spec** | ×3 | "Store imports must use only the canonical canvasStore module specifier, never an arbitrary resource-timing URL." |
| **F2-cross-source-rect-dimensions** | ×2 | "Cross-source rectangle verification must reject drift in x, y, width, or height." |
| **C1-D1** | ×2 | 「文档引用的 文件:行号 证据锚点必须真实覆盖其声称的行为,不能指向无关代码。」 |

## ⑧ 自托管操作合同（self-hosting / operational contract）

> 来源：2026-08-09 本 skill 自身真实缺陷。179 支测试的唯一正确运行命令一度**没写进任何文档**，
> 而两种直觉写法都给假红——`node --test tests/` 一支都没跑却报红（Node 24.13 把目录位置参数
> 当脚本执行，`MODULE_NOT_FOUND`），裸 `node --test` 自动发现把 `tests/fixtures/**` 下的夹具当
> 真测试收走 6 支假红。该缺陷是建完后**手查**才发现的，**不是被七面反推 + 对抗质询捞出来的**——
> 正是本 skill 声称要消灭的「后置常规命令才炸」类型。
>
> 修法（本 skill 已落地）：`scripts/run-tests.mjs` 显式枚举 `tests/*.test.mjs` 作单一权威入口，
> 文档与 CI 只指它；文档禁硬编码具体 pass 数，判据只写 `fail 0`。

质询问题（Phase 4 的 sub 拿去直接问，不写成陈述）：

1. **权威命令入档了吗？** 测试/构建/lint 的权威运行命令写进文档了吗？文档里那条命令在当前环境**实际可跑、实际给真结果**，还是只按直觉写下、从没验证过？（对照：`node --test tests/` 与裸 `node --test` 都「看起来是对的」却给假红，且连命令带假红全在文档之外）
2. **命令可跑性被实测过吗？** 文档里每条命令是否有人实际执行过并核对退出码与输出？跑一次即 `MODULE_NOT_FOUND` 的目录写法，就是「写了但没跑」的实例——文档存在 ≠ 命令可跑，`--help` 存在也 ≠ 可跑。
3. **测试自动发现边界钉死了吗？** 测试夹具/样本是否会被自动发现（裸 runner、目录扫描、shell glob）当真测试收走？若会，是否存在一条显式枚举的单一入口把发现边界钉死，而不是靠「大家记得别那样跑」？
4. **CI 与文档同源吗？** CI 配置实际执行的命令与文档声称的入口是同一条吗？文档说 A、CI 跑 B 时以哪个为准？（修法：CI 只调单一入口，文档与 CI 同源，不维护两份清单）
5. **文档硬编码了会过期的数值吗？** 文档/报告里是否写了具体 pass 数、测试数、耗时等随实现增长而漂移的数字？（本 skill 自己犯过：文档写 `174 tests`，测试涨到 179 后那句话本身成了误导源；判据只写 `fail 0` 这类不漂移的谓词）
6. **存在绕行入口吗？** 是否有绕过权威入口的「聪明写法」在文档之外流传（目录参数、自动发现、自造 exclude 参数），且没有任何机制阻止它被当成标准用法复制？
